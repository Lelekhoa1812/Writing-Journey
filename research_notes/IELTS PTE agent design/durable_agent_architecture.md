# Durable agent architecture for an IELTS/PTE writing coach

Scope: how a small Node Express app on Vercel should hold session memory, compact it, choose tool calls versus a fixed specialist pipeline, and decide what to retrieve. Current as of 24 November 2026. The app already runs seven specialist JSON evaluations and then a chat assistant. That product fact is taken from the assignment, not from a public source.

Claims below are tied to a page. Research papers describe measured methods. They are not product requirements. Blog comparisons are labelled as secondary.

## How should session memory work on a serverless host where process memory dies between requests?

### Takeaway

Each model request is stateless, and a Vercel function must not be the store for the session. The client sends a compact session on every turn. OpenAI can also keep the chain with `previous_response_id` or a Conversation, but that state lives at OpenAI, not in the Node process, and it is not a portable OpenAI-compatible feature.

### Cited Findings

- “While each text generation request is independent and stateless, you can still implement multi-turn conversations by providing additional messages as parameters to your text generation request.” Manual state is alternating user and assistant messages, or appending the previous response output to the next `input`. The guide shows this with `store: false`. — [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- For stateless reasoning-model requests, “preserve every item in the response's `output` array.” The Responses API returns encrypted reasoning items by default. Replaying the complete output keeps reasoning items and assistant `phase` values intact. Editing history that produced those items affects later reasoning. — [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- OpenAI offers two server-side alternatives to a client-held transcript. The Conversations API “persist[s] conversation state as a long-running object with its own durable identifier” across sessions, devices, or jobs. Items can be messages, tool calls, and tool outputs. `previous_response_id` chains one stored response to the next. You then pass only the new user message. — [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- Response objects “are saved for 30 days by default” and can be read from the dashboard or the API. Set `store` to `false` to disable that. “Conversation objects and items in them are not subject to the 30 day TTL.” Even with `previous_response_id`, “all previous input tokens for responses in the chain are billed as input tokens.” — [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- A separate building-agents page says the Responses API is “stateful by default, meaning you don't have to manage the conversation history on your side,” and that this is “especially helpful when you're using tools that return large payloads.” — [Building agents](https://developers.openai.com/tracks/building-agents). This does not cancel the conversation-state page. The HTTP call is still stateless. The default persistence is OpenAI storage of the response (`store` on, 30-day response TTL), not memory inside the app process.
- The Agents SDK lists four continuation strategies and says to pick one per conversation. Mixing local replay with server-managed state “can duplicate context.” `result.history` / `to_input_list()` lives in the application and fits “small chat loops.” `previousResponseId` is “the lightest server-managed continuation.” `conversationId` is shared server-managed state. An SDK `session` uses “your storage plus the SDK.” — [Running agents](https://developers.openai.com/api/docs/guides/agents/running-agents)
- In WebSocket mode, recent `previous_response_id` state is kept in a connection-local in-memory cache and is not written to disk, so it can be used with `store=false`. If that ID is not in the cache and `store=false`, “there is no persisted fallback” and the request returns `previous_response_not_found`. The recovery is a new turn with full input context. — [WebSocket mode](https://developers.openai.com/api/docs/guides/websocket-mode)
- “Vercel creates a new function invocation for each incoming request.” A later request may reuse the same instance. “Vercel scales your functions down to zero when there are no incoming requests.” — [Vercel Functions](https://vercel.com/docs/functions)
- On Fluid Compute, a warm instance can reuse global state, including a connection pool. “There is no guarantee of connection reuse” in the older one-instance-per-request model, and Fluid still spins an instance down “due to inactivity or scaling needs.” — [Connection pooling with Vercel Functions](https://vercel.com/kb/guide/connection-pooling-with-functions)
- A Vercel-maintained functions skill states the rule that follows from scale-to-zero: “never keep sessions, rooms, or caches in process memory.” It also says container instances “keep nothing between calls” and that durable state goes to an external store, not the container filesystem. The same skill gives a 4.5 MB request and response body cap, a 300-second default duration on every plan, 800 seconds maximum on Pro and Enterprise, and 30 minutes only in an extended-duration beta. — [Vercel functions skill](https://github.com/vercel/vercel-plugin/blob/main/skills/vercel-functions/SKILL.md). Treat the skill as Vercel’s summary. The lifecycle and scale-to-zero statements are also on the functions and connection-pooling pages above.
- Standalone compaction is “fully stateless”: the app sends a full context window and receives a shorter window for the next `/responses` call. Server-side compaction with `store=false` is described as Zero Data Retention friendly. The compaction item is “opaque and not intended to be human-interpretable.” — [Compaction](https://developers.openai.com/api/docs/guides/compaction)

### Inferences

- The Express process is a worker for one invocation. Module-level variables can survive only while that instance stays warm. The next chat turn can land on a new instance after idle time, a new deployment, or overflow. Session state has to arrive in the request body, or it has to be fetched from a store that outlives the process.
- Client-held history is enough for this coach. The browser already has the current task, the current draft, the seven specialist JSON results, and the chat turns. Each `/chat` request resends a compact copy. `store: false` plus that payload matches the manual pattern in the conversation-state guide. No application database is required for a single-browser session.
- A new hosted database becomes justified only when a requirement cannot be met by that payload. Examples: resume the same chat on another device that does not have the transcript; hold a draft corpus that no longer fits the 4.5 MB body cap cited in the Vercel functions skill; or share one session across workers that cannot all see the client. Until one of those is a requirement, a database is an extra store, not the memory design.
- `previous_response_id` and the Conversations API are OpenAI storage, not an app database. They fit only if the app calls OpenAI, accepts OpenAI retention (30 days for responses, no 30-day TTL for Conversation items), and can recover when an ID is missing. They are the wrong default for a generic OpenAI-compatible endpoint. The portable contract is the message array the client sends.
- Do not use the opaque compaction item as the product’s copy of the score. The UI and the next specialist still need readable JSON. The client session is that copy. An encrypted compaction item, if used at all, is only for model continuity on OpenAI.
- WebSocket continuation does not remove the serverless problem. The connection-local cache dies with the socket, and Vercel has no instance affinity across reconnects. A chat that can reconnect should send the compact session again.

### Gaps

- This research did not inspect which provider the Express app calls. If it is not OpenAI’s Responses API, `previous_response_id`, Conversations, server-side compaction, and explicit prompt-cache breakpoints may be absent. The portable design is the client message array.
- The 4.5 MB body cap and the 300-second default duration are cited from Vercel’s functions skill, not re-fetched from a dedicated limits page in this pass.
- No source here states a maximum size for a Conversation object.

## What should a compact session keep, and what should it drop, so later turns stay inside context and prefix cache stays stable?

### Takeaway

Keep the stable instructions and the rubric at the front, then append turns. Keep the current draft and the latest specialist JSON exactly. Drop superseded drafts, tool chatter, and old chat by truncation or by one compaction point. Do not rewrite scores into a looser summary, and do not compact on every turn if the prefix cache matters.

### Cited Findings

- Prompt caching reuses a prefix only when “the entire rendered prefix” matches. Eligible prefix content includes developer messages, tool definitions, and conversation history. A change “before a breakpoint” means the prefix after that change cannot match. Settings that change the rendered prefix include `model`, `tools` (names, descriptions, schemas, ordering), `parallel_tool_calls`, structured-output format, reasoning effort, verbosity, and `context_management` compaction. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- OpenAI’s caching guide says to put “stable developer instructions and shared reference material first.” Put timestamps, user-specific content, and other dynamic content “at the end rather than the beginning.” “Append new messages rather than rewriting earlier turns.” “Summarization, compaction, or context truncation can change the prefix and reset cache reuse.” — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- On GPT-5.6 and later, explicit breakpoints let the app choose where a cache write ends. Content after the last breakpoint is not written. The guide’s pattern is a 12-hour breakpoint on “shared instructions and reference material” and a 30-minute breakpoint on “session context,” with the current question after the last breakpoint. Default minimum lifetime is 30 minutes at a 1.25× write rate. A 12-hour minimum is 2.5×. Reads are 0.1× ordinary input on most of these models, and 0.05× on named GPT-6.1 and GPT-6.2 variants. Minimum cacheable prefix is 1,024 visible input tokens. Each request can create up to four cache writes. Top-level `instructions` cannot hold an explicit breakpoint. On models starting with GPT-6.2, top-level `instructions` are appended after `input` and billed uncached even on a hit. Reusable instructions belong in a developer message at the start of `input`. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Earlier than GPT-5.6, only implicit caching exists. Breakpoints are model-dependent. `prompt_cache_key` helps route requests that share a prefix. On GPT-5.6 and later, routing is automatic. A key can still separate cache accounting per user and “help prevent cache-hit probing across users.” For older models, `in_memory` retention is typically 5 to 10 minutes of inactivity, up to one hour. `24h` retention can last up to 24 hours and is the default when Zero Data Retention is off. Entries live on individual machines. Traffic above 15 requests per minute can overflow to other machines. Caches are not shared across organisations or regions. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- The compaction guide’s latency tip: after a compaction item, “you can drop items that came before the most recent compaction item.” That item “carries the necessary context.” If you use `previous_response_id`, “do not manually prune.” The example threshold is 200,000 tokens. Automatic compaction also stores `additional_tools` declarations inside the encrypted item. Request-level `tools` must be supplied again on turns that need them. — [Compaction](https://developers.openai.com/api/docs/guides/compaction)
- A 2026 EMNLP survey treats compression as Select, Compress, Store, Recover. Select decides “which subsets of the context require compression and which demand exact preservation.” Summarisation “preserves utility by semantic rewriting rather than direct deletion” and is “a primary locus of F2: In-compression Information Loss” because it can omit, over-generalise, or add inferences. Their F2 example shows mixed evidence compressed into a more confident claim. Pruning “removes content selectively while preserving the remaining structure exactly.” F3 is retrieving a similar but wrong memory after the correct item was stored. — [Context Compression for LLM Agents (EMNLP 2026)](https://aclanthology.org/2026.emnlp-main.2396.pdf)
- CliffCompaction, a 2026 methods paper about coding agents, reports that it “keeps compacted information faithful by only truncating or dropping content, never rephrasing or rewriting it,” and that it “never compact[s] a compaction.” That paper is about long coding jobs, not exam coaching. The relevant documented claim is the no-rewrite rule, not the benchmark scores. — [CliffCompaction](https://arxiv.org/abs/2609.26779)
- Acon (2025) reports 26–54% lower peak tokens on AppWorld, OfficeBench, and multi-objective QA by compressing observations and history. The method is failure-guided optimisation of natural-language compression guidelines, then distillation into a smaller model. It is a research system, not an API feature. — [Acon](https://arxiv.org/pdf/2510.00615)
- The context window counts input, output, and, on reasoning models, reasoning tokens. Extra context can cause truncated outputs. — [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)

### Inferences

- Split the prompt into two rates of change. Block A is identical for many students of the same exam and task type: coach rules, output schema, and the full rubric for that task. Block B is this student: task prompt, current draft, latest scores, and new turns. On GPT-5.6 and later, an explicit breakpoint at the end of Block A is the documented way to cache the rubric without paying a cache-write on the essay. On earlier models, the same order still matters, because implicit caching matches from the front.
- A compact session that the client stores should keep, in full and unparaphrased: exam and task type, the question, the latest student draft, the latest specialist JSON (scores and criterion comments), and the open coaching point. Those are the “exact preservation” set. A later turn that says “why did I get 6 on coherence” must see the number 6 and the comment, not a summary that might move the number.
- Drop, by deletion rather than paraphrase: every earlier full draft once the latest draft is in the session; raw specialist chain-of-thought if it was ever returned; duplicate rubric text inside chat turns; and chat turns older than a short tail, after one structured note of decisions already made (“student will fix the thesis, not the examples”). One truncation point beats a summary of a summary. That matches both the EMNLP warning on rewriting and CliffCompaction’s no-rephrase result. It conflicts with compacting every turn, which the caching guide says resets reuse from the first changed token.
- Do not put the student’s name, the draft, or a timestamp in Block A. Do not reorder or edit tool schemas between chat turns. Either change resets the cached prefix.
- If the transcript is still small, do not compact. Compaction is for when the window, latency, or bill is the problem. The OpenAI example uses a 200,000-token threshold, which a writing chat will not hit quickly. A writing coach can use a much simpler rule: keep the latest draft and the last few turns, and delete older drafts.
- Provider compaction and product compaction are different. OpenAI’s item is opaque and can carry reasoning. The client session must stay readable JSON so the app can show scores and can call a specialist again without decoding an encrypted blob.

### Gaps

- OpenAI does not publish a recommended `compact_threshold` for a tutoring chat. 200,000 is an example in the compaction guide, not a measured optimum for essays.
- No source here measures how much IELTS or PTE score accuracy drops when criterion comments are summarised. The EMNLP F2 case is a research-agent example, not an exam-scoring study.
- Cache-hit rate for a real Express deployment depends on model, volume, and region. The docs say a cache hit is not guaranteed, including when a session is maintained. This pass did not measure this app.

## When should the system use tool calls versus a fixed orchestrated pipeline of JSON specialists?

### Takeaway

Use a fixed pipeline of schema-constrained JSON calls for the seven-part evaluation. Use tool calls in the later chat only when the model must fetch or change something that is not already in the prompt. A free agent that may skip a specialist is the wrong structure for a known marking sequence.

### Cited Findings

- Structured Outputs “constrain completed, non-refusal model output” to a JSON Schema. Schema adherence is the difference from JSON mode, which only guarantees valid JSON. OpenAI says to prefer Structured Outputs over JSON mode when possible. Refusals are a separate `refusal` field and “do not necessarily follow the schema.” The app must still handle refusals, incomplete responses, API errors, and business rules the schema cannot express. — [Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- “Function calling is useful when you are building an application that bridges the models and functionality of your application,” such as querying a database or changing a UI. Structured output through the response format is “more suitable when you want to indicate a structured schema for use when the model responds to the user, rather than when the model calls a tool.” The guide’s example is a math tutoring app whose UI needs different parts of a JSON response. The short rule: connect the model to tools, functions, or data with function calling. Shape the model’s reply to the user with structured `text.format`. — [Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- A tool call is optional in the default loop. The model “may decide that it needs data or functionality provided by a tool.” The application loop is: request with tools, receive a tool call, run application code, send the tool output, receive a final answer or more calls. `tool_choice: "auto"` may call zero, one, or many tools. `"required"` forces a call. A named function forces that function. `"none"` behaves like no tools. — [Function calling](https://developers.openai.com/api/docs/guides/function-calling)
- Some current models are not available for tools on Chat Completions. “GPT-6 Astra and GPT-6.1 Sol require the Responses API for tool calling.” The Chat Completions examples in that guide use GPT-5.6 Terra. Tool search, which defers large tool lists, is only on `gpt-5.4` and later. — [Function calling](https://developers.openai.com/api/docs/guides/function-calling)
- Direct Responses API: “you want to own the loop, tool dispatch, and state handling yourself” and the workflow is “short-lived and mainly about returning the model's response.” Agents SDK: the runtime should manage turns, tool execution, guardrails, handoffs, or sessions. “You do not need to choose one globally.” — [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)
- The official agents guide repeats that split. Responses API is “calling models directly or building an agent from scratch” in your application. The Agents SDK “runs inside your application” and its runner handles the loop and handoffs. The Agents API is a managed Codex harness for long-running tasks, with OpenAI saving progress. — [Agents](https://developers.openai.com/api/docs/guides/agents)
- One SDK run is one application turn. The runner calls the model, executes tool calls, switches agent on a handoff, and stops when there is a final answer. — [Running agents](https://developers.openai.com/api/docs/guides/agents/running-agents)
- With the Responses API, “you're responsible for defining the core logic, and orchestrating the different parts.” The Agents SDK is recommended there when you want networks of agents, guardrails, and tracing, with the trade-off of less fine-grained control. The SDK “can also [be used] with other APIs and even external model providers.” — [Building agents](https://developers.openai.com/tracks/building-agents)
- Changing the `tools` array changes the cached prefix. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

### Inferences

- The seven specialists are not tools. Each one is a model call whose reply is the product: a score, a comment, or a list of errors for a known criterion. The app already knows the order. Structured Outputs match OpenAI’s tutoring example. The app should call specialist 1, validate JSON, call specialist 2, and so on. `tool_choice: "auto"` would allow the model to skip a criterion. Forcing all seven through tool calls would add a round trip per specialist without adding a decision the app does not already make.
- The chat assistant is the place for a short tool list, and only for data that is not in the compact session. A justified tool is “load the previous Task 2 draft the client did not send” or “replace the saved draft with this revision” if a draft store exists. Explaining a score, suggesting a sentence change, or quoting the rubric does not need a tool when that text is already in the prompt.
- Keep the evaluation pipeline and the chat agent as two orchestrations. The pipeline is fixed and schema-bound. The chat is one model with a stable, small tool list, or with no tools. Do not let the chat model call the seven specialists again unless the student submits a new draft. A new draft is a new pipeline run, started by application code, not by a free handoff.
- An Agents SDK handoff graph is optional packaging for the same fixed sequence. It does not change the recommendation. On a serverless request, the runner still has to finish inside the function duration, and the app still has to persist the readable JSON itself.
- If the endpoint is only Chat Completions compatible, structured `response_format` and function tools are the features to rely on. Responses-only tool calling, as documented for GPT-6 Astra and GPT-6.1 Sol, is not the portable path.

### Gaps

- OpenAI does not publish a quality comparison of “seven schema calls in fixed order” versus “one agent that may call seven tools” on writing assessment.
- This pass did not measure latency or cost of seven sequential calls against one call with a combined schema. The architectural distinction is about who is allowed to skip a step, not about which is cheaper.

## What retrieval is worth adding for exam rubrics and the student's own past drafts, and what is extra?

### Takeaway

Put the one rubric that applies to this task in the stable prompt prefix. Do not retrieve it. Keep past drafts in the client session as exact text plus the score JSON. Add search only when the client cannot send the essay the student is asking about. A vector store of public band descriptors is extra and can split a short rubric into chunks.

### Cited Findings

- File search is a hosted Responses tool. The model searches vector stores “through semantic and keyword search.” “When the model decides to use it, it will automatically call the tool.” The app does not run that search. The response can include a `file_search_call` and a message with citations. Result count can be limited “to reduce both token usage and latency, but may come at the cost of reduced answer quality.” Search results are omitted unless `include` asks for them. — [File search](https://developers.openai.com/api/docs/guides/tools-file-search)
- The Retrieval API is application-run semantic search over a vector store. “This flexibility makes semantic search a powerful technique for querying knowledge bases of any size.” Default maximum is 10 results. The maximum is 50. Attribute filters run before the semantic search. A file can carry an attributes map. Adding a file “will be automatically chunked, embedded, and indexed.” Storage is charged from parsed chunks and embeddings. After search, the app can pass the chunks to a model. That second call is optional. — [Retrieval](https://developers.openai.com/api/docs/guides/retrieval)
- Default chunking is `max_chunk_size_tokens` 800 and `chunk_overlap_tokens` 400. Limits are 100 to 4096 tokens per chunk. Overlap should not exceed half the chunk size. Maximum file size is 512 MB and 5,000,000 tokens. — [Retrieval](https://developers.openai.com/api/docs/guides/retrieval)
- A `score_threshold` from 0.0 to 1.0 “will limit the results to more relevant chunks, though it may exclude some potentially useful ones.” Hybrid search can weight embedding similarity against keyword overlap. — [Retrieval](https://developers.openai.com/api/docs/guides/retrieval)
- Prompt caching treats “shared reference material” as prefix content that should stay stable and sit at the front. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- The EMNLP survey’s F3 case: the right memory was stored, retrieval returned a different item that was topically similar and temporally wrong, and the agent used the wrong item. — [Context Compression for LLM Agents (EMNLP 2026)](https://aclanthology.org/2026.emnlp-main.2396.pdf)
- A secondary write-up of the OpenAI docs distinguishes three paths: direct file input when the file is known, the Retrieval API when application code must search and filter, and the `file_search` tool when the model should decide to search. It says this is a control boundary, not a measured ranking of quality or cost. — [Choosing between file input, retrieval, and file search](https://blog.rodytech.ai/choosing-between-openai-file-input-retrieval-and-file-search/). Use it as a map of the official pages, not as an independent result.

### Inferences

- The rubric for one IELTS or PTE task is known before the model runs. The app can select “IELTS Writing Task 2” or “PTE essay” in code and insert that descriptor text into Block A. That gives the model the whole scale, keeps band wording exact, and makes the prefix cacheable. File search would let the model skip the lookup or return a chunk that is not the adjacent band. Default 800-token chunks with 400-token overlap can cut a short public rubric apart. Nothing in the retrieval guide says to do that for a document that already fits in the prompt.
- The student’s current draft and the specialist JSON should also be inserted whole. They are the object being marked. Semantic search over that one essay does not answer a criterion question better than the essay itself.
- Past drafts are worth a compact client record: date, exam, task type, scores, and the persistent error the coach is tracking, plus the full text of the latest draft. When the student says “compare this with last week,” the client sends that earlier draft in the request. That is still client-held history. It does not need a vector store.
- Retrieval becomes worth adding when the student has more drafts than the request can carry, or when the question is open (“find where I keep dropping articles”) and the app cannot know which draft to attach. Then the Retrieval API, not `file_search`, matches the control OpenAI documents: the app searches, filters by an attribute such as task type or date, and inserts the returned text. Hosted `file_search` is extra here because a missed tool call would let the coach answer from memory of the rubric or from the wrong essay. The EMNLP F3 case is the failure mode: a similar chunk is not the student’s last Task 2.
- A vector store is a hosted store with a storage charge. It is the same class of extra system the assignment says not to add while the client can hold the history. Do not add one for rubrics. Add one for past drafts only after client-held history cannot carry the essays the coach must see. If that store is added, filter by student and task before ranking, and pass the selected draft as exact text, not as a paraphrase.
- Also extra for this app: web search for band scores, a shared vector store of other students’ essays, and retrieval on every chat turn “in case.” Stable rubric text in the prefix already covers the marking criteria. Another student’s essay is the wrong memory item.

### Gaps

- This pass did not measure token counts for the official IELTS or PTE public descriptors, so it does not state that they are under the 1,024-token cache minimum. If a single rubric is shorter than the model’s minimum cacheable prefix, caching still works once stable instructions plus the rubric cross that minimum. The docs require the prefix length. They do not require the rubric alone to meet it.
- No primary source in this pass says “never use RAG under N tokens.” The recommendation to inline the rubric is an inference from who selects the document, from chunk defaults, and from the caching guide’s treatment of reference material.
- Copyright and exam-board licence terms for storing official descriptors in a prompt or a vector store were not reviewed.

## Which 2025-2026 patterns are appropriate for a small Express app?

### Takeaway

Use structured outputs for the specialists, a client-held append-only session, and a stable prompt prefix so provider caching can work. Use OpenAI compaction only after the transcript is large, and only beside a readable session. Use a durable workflow only if a multi-step run must survive a crash or a deploy. Do not adopt a research compressor or a managed agent harness for this chat.

### Cited Findings

- Structured Outputs are the current replacement for JSON mode on `gpt-4o-2024-08-06` and later, including the Responses and Chat Completions APIs. New projects are told to start with `gpt-6.2-astra`. JSON mode remains for older models. — [Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- Prompt caching is on by default for supported OpenAI models. It caches key-value tensors for a prefix, not the text. Agents API model calls use the same caching rules, and “maintaining a session doesn't guarantee a cache hit.” GPT-5.6 and later add explicit breakpoints and a choice of 30-minute or 12-hour minimum lifetime. A 12-hour option is also recorded in the API changelog for `/v1/responses`. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), [Changelog](https://developers.openai.com/api/docs/changelog)
- Compaction is a current Responses feature: `context_management` with `compact_threshold` during generation, a `compaction_trigger` item, or `POST /responses/compact` for a stateless window. The caching guide lists compaction as a change that can block reuse from the first changed token. — [Compaction](https://developers.openai.com/api/docs/guides/compaction), [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Vercel Workflows run multi-step logic that can “retry failed steps, wait for external events, and resume across crashes and deployments.” Vercel manages persistence and dispatches steps with Vercel Queues. The open-source Workflow SDK is the code (`"use workflow"` and `"use step"`). Vercel Workflows is the managed service. The same docs say to use Workflows when steps must survive crashes and deployments, when they wait minutes to months, or when they wait for an external event. Use Queues for independent jobs that need retries. Use Schedules for cron. A chat-sized job is not in that list. — [Vercel Workflows](https://vercel.com/docs/workflows)
- Express is a documented Workflow SDK target, but not as a plain `node server.js` deploy. The getting-started guide installs `workflow`, `express`, `nitro`, and `rollup`, adds a `nitro.config.ts` with the `workflow/nitro` module, and uses `start()` from a route. `start()` “returns immediately after enqueuing the workflow. It doesn't wait for the workflow to complete.” Steps retry unless the code throws `FatalError`. `sleep` suspends without using compute. — [Workflow SDK for Express](https://workflow-sdk.dev/docs/getting-started/express), [`start`](https://workflow-sdk.dev/docs/api-reference/workflow-api/start)
- The agents guide’s managed Agents API adds “automatic context compaction, multi-agent orchestration, programmatic tool calling,” and a hosted or self-hosted sandbox. State between tasks is an OpenAI-saved session. That is a different runtime from an Express function. — [Agents](https://developers.openai.com/api/docs/guides/agents)
- Research compaction in 2025–2026 is real and narrow. Acon needs a failure-analysis loop and a distilled compressor. SumOne trains a summariser with masked reconstruction and reports large cost cuts on DeepSearchQA and SWE-bench, with a small absolute quality drop, for search and software-engineering agents. CliffCompaction targets coding agents and million-token sessions. The EMNLP 2026 survey’s point for builders is the failure split (wrong thing kept, lossy rewrite, wrong thing retrieved), not a library to install. — [Acon](https://arxiv.org/pdf/2510.00615), [SumOne](https://arxiv.org/abs/2611.06445v1), [CliffCompaction](https://arxiv.org/abs/2609.26779), [EMNLP 2026 survey](https://aclanthology.org/2026.emnlp-main.2396.pdf)

### Inferences

- Appropriate now, inside the existing Express app: one request builds Block A (stable rules and the selected rubric) and Block B (client session). Specialists use strict JSON Schema. The chat call appends to that same session. The response returns the updated compact session so the client can store it. No new database, no workflow runtime, no vector store.
- Prompt caching is appropriate as a layout rule even before explicit breakpoints. Stable tools and rubric first, student text last, no rewrite of earlier turns. Explicit `prompt_cache_options` and 12-hour TTL are appropriate only on OpenAI GPT-5.6 or later, for Block A, if that prefix is at least 1,024 tokens and is reused across students of the same task. A per-student `prompt_cache_key` is appropriate on older models for routing, and on newer models to keep one student’s cache accounting separate. Do not assume a non-OpenAI compatible endpoint implements any of this.
- Compaction is appropriate later, as an app rule: when the client session approaches a size you choose, delete old drafts and old turns and keep the exact score card. OpenAI’s `/responses/compact` is appropriate only on that API, with `store: false` if retention matters, and never as the only copy of the score. Compacting every turn would fight the prefix cache.
- A durable workflow is appropriate only if the seven specialist calls must resume after a timeout, a crash, or a deploy, or if a human must approve a step hours later. It is a poor fit for the chat turn the user is waiting on, because `start()` does not wait for the result, and the Express guide adds Nitro and a build. Retrying a whole evaluation from the client is the smaller design while runs finish inside the function duration. If a later measurement shows the seven calls exceed that duration, a workflow is the documented Vercel escape, not a longer in-memory session.
- Not appropriate for this app: the Agents API sandbox, a standing tool-using marker that chooses which criteria to run, learned compressors (Acon, SumOne), and a vector index of rubrics. Those patterns target long-horizon or open-corpus agents. This coach has a known sequence and a known short rubric.

### Gaps

- No source in this pass gives a 2026 benchmark of writing-tutor accuracy under compaction. Transfer from coding-agent papers is not established.
- Workflow SDK pricing and whether this Express app’s current Vercel setup already has Nitro were not checked.
- Provider support for `response_format: json_schema` on the app’s actual model was not checked. The OpenAI guide limits that feature to `gpt-4o-2024-08-06` and later.
